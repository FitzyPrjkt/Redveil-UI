# redveil-ui 0.2.0 — Design Spec

**Date:** 2026-09-07
**Status:** Draft, pending review
**Scope:** redveil-ui 0.2.0 (post-0.1.6)
**Target release:** TBD (after spec approval + implementation plan)

---

## 1. Overview

This spec covers the design for `redveil-ui` 0.2.0. It is the second minor
release after 0.1.0/0.1.x and addresses four areas of debt and risk that
have been acknowledged as known limitations in the 0.1.x line, plus a
narrowly-scoped expansion of the deployment surface.

The 0.1.x line shipped as feature-complete for the documented surface:
all 15 routes render, 1101/1101 library tests pass, 19/19 dashboard e2e
tests pass on a fresh install in a clean venv. 0.2.0 is the first release
that touches what was previously described as a "personal single-user,
localhost-only" deployment.

The headline change is **opt-in LAN exposure with a single-API-key
auth layer**, gated by a hard fail-closed check at server startup.
The auth surface is intentionally minimal — no multi-user, no
sessions-as-identity, no SSO — because the project identity remains
"single operator". Multi-user deployments are explicitly out of scope
and delegated to reverse-proxy + external auth provider.

The other major change is **operational hardening under load**:
SQLite is moved to WAL mode with busy-timeout and retry-on-lock, the
previously-stubbed scan control endpoints are wired to the underlying
orchestrator, and a startup recovery sweep handles scans left in
`'running'` state by a crashed server.

The remaining items (audit log, rate limiting, improved health
endpoint, false-positive UI toggle, strict security headers) are
smaller and treated as defense-in-depth around the headline change.

---

## 2. Non-goals (explicitly out of scope for 0.2.0)

The following are **not** in this spec and will not be implemented in
0.2.0:

- **Multi-user, multi-identity, role-based access control.** The project
  identity is "single operator". Multi-user deployments are delegated
  to reverse proxy + external auth provider (e.g. Caddy + Authelia).
- **OAuth, OIDC, SSO, SAML.** Same reason.
- **Self-signed TLS certificate generation.** Tracked as a future
  0.3.0 opt-in feature. See §10.4.
- **Migrating from SQLite to a different database engine.** SQLite is
  the right fit for the single-operator model; WAL + retry is enough.
- **WebSocket-based live updates.** SSE stays as the streaming
  transport. Switching to WS would change the browser API surface for
  no real benefit.
- **Frontend framework swap (e.g. Next.js → something else).**
- **Scan scheduling / cron / automation features.** These are
  operational conveniences that belong to the underlying `redveil` CLI,
  not the dashboard.

---

## 3. Project scope decision (binding for this spec)

**Decision: Option C — Hybrid. Localhost default, LAN opt-in.**

The 0.1.x deployment model is preserved by default. LAN exposure is
available behind a deliberate configuration change. The change of
`bind` from loopback to a non-loopback address triggers a hard
fail-closed check at server startup: the server refuses to start
unless `auth.api_key` is set in the config or via the
`REDVEIL_UI_API_KEY` environment variable.

This is the only model that the spec designs for. The other options
considered were rejected:

- **Option A (localhost-only, no auth):** Rejected because it forces
  the operator to roll their own auth (e.g. reverse proxy) for any
  legitimate LAN use case. The auth surface in the spec is small
  enough to not warrant rejection.
- **Option B (LAN first-class, multi-user):** Rejected because it
  changes the project identity from "personal single-user tool" to
  "small-team tool", which is a far larger commitment than what the
  0.2.0 release is intended to be. Multi-user is achievable today
  with a reverse proxy + Authelia, and that is the recommended path
  until/unless the project explicitly pivots.

The implications of Option C flow through the rest of this spec.

## 4. Reliability: SQLite WAL + retry-on-lock + recovery sweep

### 4.1 Problem

Single-writer SQLite locks under the current write pattern. The
evidence log path writes one row per request per scan; under a high
`max_requests` budget with many concurrent orchestrator actions, the
single-writer model produces `database is locked` errors that the
current scanner does not retry.

This was already listed as a known limitation in 0.1.x. It blocks
any meaningful load test of the rest of the spec.

### 4.2 Solution

Three coordinated changes:

1. **WAL mode on every connection.** Use SQLAlchemy's
   `event.listens_for(Engine, "connect")` to issue
   `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;` immediately
   after each new aiosqlite connection is established. The pragma
   `journal_mode=WAL` is persistent at the database file level once
   set, but it must be re-issued per connection to be safe under
   connection reuse and fork scenarios. The `busy_timeout` is per-connection.

2. **Retry-on-lock at the write path.** Wrap insert-heavy
   operations in a small retry decorator that catches
   `sqlalchemy.exc.OperationalError` whose `.args[0]` starts with
   `'database is locked'`, sleeps with exponential backoff
   (50ms → 200ms → 500ms, three attempts), and either succeeds or
   raises. The retry lives in the database session layer, not in
   the route handlers.

3. **Startup recovery sweep.** On server startup, query the `scans`
   table for rows with `status = 'running'`. For each, transition to
   `status = 'failed'` with `error = 'recovered from unclean shutdown
   at <ISO timestamp>'` and emit a warning log line. This prevents
   the dashboard from showing a permanently-"running" scan that is
   actually dead. The recovery sweep runs in a startup task before
   the FastAPI app begins accepting requests.

### 4.3 Files affected

- `redveil_ui/api/db.py` — add connect-listener, retry decorator
- `redveil_ui/api/lifespan.py` (or wherever the FastAPI lifespan
  context is) — add recovery sweep at startup
- New test file `tests/test_db_retry.py` — covers retry-on-lock
  using a mock that raises the right exception shape

### 4.4 Acceptance

- A test that holds an exclusive lock on the SQLite file for
  200ms and then releases it observes the write succeeding
  without the route returning 500.
- After a simulated crash mid-scan, the next server start shows
  the scan as `failed` with the recovery message in the dashboard.

## 5. Operational: Scan control endpoints (start/stop/status)

### 5.1 Problem

The endpoints under `/api/lab` (`POST /start`, `POST /stop`,
`GET /status`) are currently stubs that return 501. The same is
true of `POST /api/config/reset`. There is no way to stop a
running scan from the UI or the API. This is a real operational
hazard: a scan in `active` profile that goes off the rails must
either run to completion or be killed by killing the server
process (which leaves the DB row in `'running'` state and is what
the recovery sweep in §4.2.3 is meant to clean up).

### 5.2 Solution

Wire the existing stubs to the underlying orchestrator. The redveil
library's orchestrator exposes cancel semantics; this spec assumes a
`scan_id → cancel` signal that the UI layer can invoke. If that
signal does not exist in the library as of 0.2.0 work, the spec is
**gated** on adding it to the library first (a separate, smaller PR
that lands before this 0.2.0 work begins). Without a cancel signal
in the library, §5 cannot be implemented and the operational
hazard (§5.1) remains.

**Endpoint names — REST-aligned, per-resource actions:**

The 0.1.x codebase has 501 stubs under `/api/lab/*` (see
`redveil_ui/api/routes/lab.py`). The `/api/lab/*` namespace is
semantically reserved for **lab environment control** (e.g.
starting/stopping a vulnerable test target like DVWA or Juice
Shop) — a future feature unrelated to scan lifecycle. The 0.2.0
scan-control endpoints therefore do **not** live under
`/api/lab/*`. They are sub-resource actions on the scan
itself, following the same per-resource pattern that 0.1.x
already established for read-side endpoints
(`/api/scans/{id}/findings`, `/api/scans/{id}/stream`,
`/api/scans/{id}/evidence`).

Concrete endpoints:

- `POST /api/scans/{scan_id}/start` — start a scan that was
  previously created in `pending` state. Idempotent: if the
  scan is already `running`, return 200 with the current
  state. Body: empty. Path parameter: `scan_id` (integer).
- `POST /api/scans/{scan_id}/cancel` — signal the
  orchestrator to cancel an in-flight scan. Returns 202
  Accepted on dispatched cancellation; the scan's row
  transitions to `cancelled` (see §11.1) once the
  orchestrator acknowledges. Path parameter: `scan_id`
  (integer). Idempotent: cancelling an already-`cancelled`
  or terminal-state scan returns 200 with the current state
  (not 202, not an error).
- `GET /api/scans` (existing 0.1.x endpoint, no change) —
  the fleet-level scan list, with optional status filter.
  Combined with `/healthz` (§9) which returns
  `scans_{pending,running,completed,failed,cancelled}`
  counts, this provides the same fleet-level summary that
  the 0.1.x `GET /api/lab/status` stub was intended to
  provide. **The `/api/lab/status` endpoint is not part of
  this spec**; if it exists as a 501 stub in
  `redveil_ui/api/routes/lab.py`, it is left untouched
  (still 501) and reserved for a future lab-environment
  feature. Do not reuse it for scan fleet status.
- `POST /api/config/reset` — reset the config to the values
  present at the last successful `init`. The endpoint
  refuses to start the reset if the running server is
  currently bound to a non-loopback address and the reset
  would change `bind` from `0.0.0.0` back to `127.0.0.1` —
  in that case the auth state would also need to be
  invalidated, which is a separate operator action
  (`redveil-ui rotate-key`). The endpoint returns 409
  Conflict in that case with a message pointing to the
  rotate-key subcommand.

### 5.3 New status value: `cancelled`

The `scans.status` column gains a new value: `cancelled`. The
existing values (`pending`, `running`, `completed`, `failed`) are
unchanged. The UI's status pill component gains a new color and
label for `cancelled`.

### 5.4 Files affected

- `redveil_ui/api/routes/scans.py` — add `POST /api/scans/{scan_id}/start`
  and `POST /api/scans/{scan_id}/cancel` route handlers
- `redveil_ui/api/routes/lab.py` — **unchanged** in 0.2.0; the
  501 stubs stay as-is. They are not in scope.
- `redveil_ui/api/routes/config.py` — replace `/reset` 501
- `redveil_ui/api/scanner.py` — wire the library's cancel signal
- Migration script that adds `cancelled` to the `scans.status`
  enum check constraint (or removes the constraint if there isn't
  one, depending on what the schema currently is)

### 5.5 Acceptance

- Starting a scan and immediately calling
  `POST /api/scans/{scan_id}/cancel` results in the scan
  transitioning to `cancelled` within 2 seconds.
- The dashboard's scan detail page shows a `Cancel` button for
  scans in `running` state.

**Response matrix for `POST /api/scans/{id}/cancel`:**

| Current status of scan | HTTP response | Body | Why |
|---|---|---|---|
| `running` | 202 Accepted | `{"status": "cancelled", "scan_id": N}` (eventual, after orchestrator acknowledges) | Normal case — cancel signal dispatched |
| `pending` | 202 Accepted | same as above | Scan was queued; cancel before start succeeds |
| `cancelled` | 200 OK | `{"status": "cancelled", "scan_id": N, "idempotent": true}` | **Idempotent** — desired state already reached |
| `completed` | 409 Conflict | `{"error": "scan is in terminal state 'completed' (started ..., completed ...); cannot cancel a finished scan"}` | **State conflict** — scan finished before the cancel arrived; user must be told their action had no effect because there was nothing to cancel |
| `failed` | 409 Conflict | same shape, with `terminal state 'failed'` | Same reasoning |

**Response matrix for `POST /api/scans/{id}/start`:**

| Current status of scan | HTTP response | Body | Why |
|---|---|---|---|
| `pending` | 202 Accepted | `{"status": "running", "scan_id": N}` | Normal case — start dispatched |
| `running` | 200 OK | `{"status": "running", "scan_id": N, "idempotent": true}` | **Idempotent** — already in desired state |
| `completed` / `failed` / `cancelled` | 409 Conflict | `{"error": "scan is in terminal state 'X'; cannot restart a finished scan. Create a new scan instead."}` | **State conflict** — terminal-state scans cannot be restarted. The error message directs the user to the correct action (create a new scan via `POST /api/scans`). |

**Why distinguish 200 from 409:** Returning 200 for "cancel of
already-completed scan" would mislead the operator into thinking
they just cancelled something that was actually finished minutes
ago. The action had no effect because there was nothing to cancel;
that is a state conflict (the precondition for the action is not
met), not a successful no-op. 409 Conflict is the correct status
code for "request is well-formed and the server understood it,
but the current state of the resource does not permit the
requested transition" (RFC 9110 §15.5.10).

**Why allow 200 for "cancel of already-cancelled" specifically:**
Cancelling a cancelled scan has a well-defined identity — the
desired terminal state is `cancelled`, and the scan is already in
that state. The action succeeded in the sense that the scan is
in the state the operator wanted. This is the textbook case for
idempotency. By contrast, "cancel a completed scan" has no
well-defined identity because the operator's mental model
(there is an in-flight scan to cancel) is wrong.

## 6. Security: Auth layer

### 6.1 Threat model

The auth layer exists to ensure that **only the operator** can
trigger destructive operations (L3+ scans, custom payload probes,
target deletion) when the server is bound to a non-loopback address.

The threat being defended against is an attacker on the same
network who can reach the listening port. Out-of-scope threats
include: an attacker who has compromised the host itself, an
attacker with physical access, and an attacker on a different
network who can reach the server via port forwarding (the spec
treats that as "exposing to the public internet" and explicitly
warns against it in the README).

The LAN-mode HTTP variant has an additional known limitation:
the session cookie is transmitted in plaintext on the LAN. The
session is bound by:

- 24-hour expiry
- HttpOnly flag (no JS access)
- SameSite=Strict (no cross-site request)
- HMAC value rather than the raw key (the key never leaves the
  server after the initial POST to `/api/auth/login`)

This is acceptable for the single-operator model where the LAN is
under the operator's control (home, isolated lab). It is not
acceptable for untrusted networks (public WiFi, conferences,
multi-tenant LANs). The README's LAN deployment section states
this explicitly. The recommended deployment for those cases is a
reverse proxy terminating TLS in front of redveil-ui.

### 6.2 API key generation and storage

The API key is generated by `redveil-ui init` and shown to the
operator exactly once. The operator must save it before the
prompt continues. The key format is `rvui_<32 hex chars>`
(128 bits of entropy, self-identifying for log greps).

Three storage locations, in order of decreasing precedence at
request time:

1. `REDVEIL_UI_API_KEY` environment variable (raw plaintext,
   overrides everything)
2. `~/.redveil-ui/.api_key` file (raw plaintext, mode 0600, owned
   by the user account that runs `redveil-ui start`)
3. `auth.api_key_hash` field in `~/.redveil-ui/config.yaml`
   (sha256 hex digest, used only for validation; the raw key is
   never reconstructed from this)

The validation path always compares the supplied key against the
hash, regardless of which storage location supplied it.

### 6.3 Auth flow

#### 6.3.1 Browser (LAN mode)

```
GET /                                 → 401 + redirect to /login (UI)
POST /api/auth/login                  → 200 Set-Cookie (HttpOnly, SameSite=Strict,
                                          Secure conditional on effective scheme,
                                          Max-Age=86400)
GET /api/scans                        → cookie auto-included → 200
POST /api/auth/logout                 → 200 Set-Cookie expires=now
```

The cookie value is a dot-separated string of
`{issued_at_unix}.{hmac_hex}`, where the HMAC is
`HMAC-SHA256(key=raw_api_key, message=str(issued_at_unix))`
truncated to 32 hex chars. The server validates by splitting
the cookie on `.`, recomputing the HMAC with the same
`issued_at` value and the API key (loaded from one of the
three storage locations per §6.2), and comparing in constant
time. The `issued_at` is checked to be within `session_ttl_seconds`
of `now()`; older cookies are rejected. The same validation
runs whether the cookie was set via `/api/auth/login` or sent
in via the `X-API-Key` header — the header value is treated as
if it were the raw API key, and the middleware performs the
same HMAC comparison to derive the effective "session" identity
for the audit log (§7.2).

#### 6.3.2 CLI / curl / CI (LAN mode)

```
curl -H "X-API-Key: rvui_..." http://host:port/api/scans
```

The middleware accepts the API key via either the cookie or the
`X-API-Key` header. The header is the only option for non-browser
clients. The middleware never accepts both: the cookie takes
precedence if present.

#### 6.3.3 Localhost mode

All of the above is bypassed. The middleware short-circuits when
the request's effective client IP is in `127.0.0.0/8` or `::1/128`.
No auth is required for any operation. This preserves the 0.1.x
behaviour exactly.

### 6.4 Conditional Secure flag

The Set-Cookie response includes the `Secure` flag if and only if
the request that triggered it was served over HTTPS. The "effective
scheme" is computed as:

```
effective_scheme = (
    request.url.scheme == "https"
    or request.headers.get("X-Forwarded-Proto", "").lower() == "https"
)
```

A direct HTTPS request (which the 0.2.0 server does not itself
serve, but which a reverse proxy might present) results in a
Secure cookie. A direct HTTP LAN request results in a non-Secure
cookie. A request through a reverse proxy that sets
`X-Forwarded-Proto: https` also gets a Secure cookie.

This is the only correct behaviour. Setting `Secure` unconditionally
would break the auth flow on plain HTTP LAN (the browser would
silently refuse to store the cookie). Omitting `Secure`
unconditionally would send the cookie over HTTP, which is the
documented limitation of LAN mode without TLS.

### 6.5 Auth gating by destructive level

The middleware (or a thin per-route dependency) classifies each
incoming mutation request as either non-destructive or destructive
based on the request body:

- `profile == "active"` → destructive
- `max_destructive_level ∈ {"L3", "L4", "L5", "L6"}` → destructive
- `allow_destructive == true` → destructive

In localhost mode, this classification is recorded in the audit
log (§9) but does not block any request.

In LAN mode, a request classified as destructive is rejected with
`401 Unauthorized` if no valid auth is present. Non-destructive
requests in LAN mode (e.g. viewing the dashboard, listing past
scans) are allowed without auth. The reasoning: a passive observer
on the LAN can already do everything that a non-destructive
redveil-ui request does, including `curl` against the target. The
auth exists to prevent the LAN observer from sending payloads.

Custom payload probes (`POST /api/probes/custom`) are always
classified as destructive and always require auth in LAN mode,
regardless of `profile` field. The existing
`confirmed_dwyor: true` check is unchanged.

### 6.6 Init-time LAN warning

When `redveil-ui init` detects that the user has set
`bind: 0.0.0.0` (or any non-loopback address) in the new config
or via a CLI flag, it shows a Y/n prompt before completing init:

```
⚠️  You are configuring redveil-ui for LAN exposure.

   In this mode, every request reaches the server over your
   network without encryption (unless a reverse proxy terminates
   TLS in front). The session cookie is transmitted in plaintext
   on the LAN. This is acceptable for trusted home/lab networks
   and not acceptable for public WiFi, conferences, or shared
   LANs with untrusted users.

   (Advanced: you can add HTTPS in front of redveil-ui using
   Caddy or Traefik — see the "LAN deployment" section in the
   README for the one-line config. The browser will then show
   the lock icon and cookies are encrypted on the wire.)

   Continue with LAN exposure? [y/N]:
```

If the user answers `n` (or non-`y`), init aborts and no config
is written. If the user answers `y`, init proceeds and writes
a line to `~/.redveil-ui/security.log`:

```
2026-09-07T12:34:56Z LAN_EXPOSURE_CONFIRMED user=fitzydev bind=0.0.0.0 port=8000 source=interactive
```

If `--yes` is passed to `init`, the prompt is skipped (consistent
with the existing DWYOR skip flag), but the security.log line is
still written with `source=auto_acknowledged`:

```
2026-09-07T12:34:56Z LAN_EXPOSURE_CONFIRMED user=fitzydev bind=0.0.0.0 port=8000 source=auto_acknowledged
```

The interactive prompt is **not** a typed-confirmation gate like
the destructive-scan DWYOR gate (`I ACKNOWLEDGE DWYOR`); a Y/n
prompt is sufficient because the risk is informational, not
authorising a destructive action.

### 6.7 Files affected

- `redveil_ui/api/middleware.py` (new) — auth middleware, CSP
  headers, rate limit setup
- `redveil_ui/api/routes/auth.py` (new) — `/api/auth/login`,
  `/api/auth/logout`
- `redveil_ui/cli.py` — `rotate-key` subcommand
- `redveil_ui/first_run.py` — generate API key, interactive LAN
  warning, write security.log entry
- `redveil_ui/server.py` — fail-closed check at startup, install
  middleware
- `redveil_ui/api/scanner.py` — auth classification in the
  destructive-level gate

### 6.8 Acceptance

- Server refuses to start with `bind: 0.0.0.0` and no API key in
  any of the three storage locations. Error message is clear and
  mentions how to set the key.
- Server starts with `bind: 0.0.0.0` and API key set.
- Browser login flow works end-to-end on HTTP LAN. Cookie is set
  with HttpOnly + SameSite=Strict but no Secure flag. Subsequent
  requests within 24h are authenticated.
- Reverse proxy with TLS termination in front works: cookie gets
  Secure flag because `X-Forwarded-Proto: https` is set.
- L3+ scan creation in LAN mode without auth returns 401. With
  auth, succeeds.
- L1-L2 scan creation in LAN mode without auth succeeds (logged
  in audit log).

## 7. Security: Rate limiting + audit log

### 7.1 Rate limiting

Add `slowapi` as an explicit dependency (verify whether it is
already transitively present; if so, no dep change) and use it
to apply a per-IP token bucket:

- 60 requests per minute per IP for all routes (default)
- 10 requests per minute per IP for `POST /api/probes/custom` and
  `POST /api/scans`
- 5 requests per minute per IP for `POST /api/auth/login` (to
  slow brute-force attempts)

Rate limits apply in both localhost and LAN modes. The localhost
default is permissive enough not to interfere with the e2e test
suite; LAN mode applies the same limits.

The limiter must NOT trust `X-Forwarded-For` for client-IP
identification unless the source IP is in a configurable
"trusted proxy" list (default: `127.0.0.1/32` and `::1/128`).
The list is set in `config.yaml` under `rate_limit.trusted_proxies`.
This prevents an attacker from spoofing their IP via the header
to bypass per-IP rate limits.

The rate limiter must redact the `X-API-Key` header from any logs
it emits.

### 7.2 Audit log

Every destructive action in LAN mode is written to a new
`audit_log` SQLite table:

```sql
CREATE TABLE audit_log (
    id          INTEGER PRIMARY KEY,
    ts          TEXT NOT NULL,                   -- ISO 8601 UTC
    actor       TEXT NOT NULL,                   -- "anonymous" or the API key suffix (last 4 hex)
    action      TEXT NOT NULL,                   -- see action enum below
    target_kind TEXT,                            -- "scan", "target", "finding"
    target_id   TEXT,                            -- string id of the target entity
    request_meta TEXT,                           -- JSON: {client_ip, user_agent, request_path}
    result      TEXT NOT NULL,                   -- "allowed" or "denied"
    deny_reason TEXT                             -- populated if result="denied"
);
```

**`action` enum (authoritative):**

- `scan.create` — new scan submitted
- `scan.cancel` — operator cancelled an in-flight scan
  (especially relevant for L3+ where cancellation is a deliberate
  termination of a destructive process)
- `scan.delete` — scan record deleted
- `probe.custom` — custom payload probe via `/api/probes/custom`
- `target.create` / `target.delete` / `target.update`
- `finding.suppress` / `finding.unsuppress` — FP toggle operations
- `auth.login` / `auth.logout` / `auth.rotate_key` / `auth.fail`
- `audit.rotate` — the audit log's own rotation event
- `lan.exposure_confirmed` — mirrors the security.log line in §6.6
  for unified querying; written from the same code path that
  writes to `security.log`

This list is **not exhaustive** but every action that has an
`auth` implication (LAN mode required) or that modifies the
operator's audit-relevant state must appear in it. Adding a new
`action` value is a code change in
`redveil_ui/api/middleware.py` (or wherever the audit write
lives) plus a new test in §14.

**Scope boundary:** The `audit_log` table is for **operator
actions that affect state** (auth, scan creation, scan
cancellation, FP suppression). It is **not** for the scan
lifecycle events (started/completed/failed/cancelled) themselves
— those go to the SSE stream per §11.1.1 B8/B10. The two
streams are separate by design:

- SSE events: per-scan, real-time, transient (consumed by the
  browser, not persisted for query)
- audit_log: per-action, durable, queryable, append-only

If the spec author later wants scan lifecycle events queryable
after the SSE stream has been consumed (e.g. for "show me all
scans cancelled in the last 7 days"), that is a separate
`scan_event_log` table for 0.3.0+, not a use of `audit_log`.

In localhost mode, the audit log is also written (it costs
nothing), with `actor = "loopback"`.

A new dashboard view (`/audit-log`) shows the last 100 entries
with filters for actor, action, result. This view is itself
read-only and requires no auth (reading your own audit log is not
a destructive action).

The audit log is **append-only**. There is no UI to delete entries.
A `redveil-ui audit-rotate` subcommand truncates entries older
than 90 days; this is the only deletion path and it is logged
itself in the same table (`action = "audit.rotate"`).

### 7.3 Files affected

- `redveil_ui/api/middleware.py` — rate limit + audit log writes
- `redveil_ui/api/routes/audit.py` (new) — `/api/audit` and
  `/api/audit` HTML view
- `redveil_ui/api/db.py` — `audit_log` table creation in
  `init_db`
- `redveil_ui/cli.py` — `audit-rotate` subcommand
- Frontend: new page at `/audit-log`

## 8. Security headers and CSP

A single middleware in `redveil_ui/api/middleware.py` adds the
following headers to every response, in both localhost and LAN
modes:

```
Content-Security-Policy: default-src 'self';
```

## 9. Observability: Health endpoint

`GET /healthz` currently returns `{"status": "ok"}` without
actually checking anything. The 0.2.0 version:

```python
@app.get("/healthz")
async def healthz(session: AsyncSession = Depends(get_session)) -> dict:
    db_ok = (await session.execute(text("SELECT 1"))).scalar() == 1
    last_scan = (
        await session.execute(
            text("SELECT created_at FROM scans ORDER BY created_at DESC LIMIT 1")
        )
    ).scalar()

    # Counts by status — explicitly enumerate all 5 valid statuses
    # so `cancelled` is not silently dropped or merged with `failed`.
    status_counts = {}
    for status in ("pending", "running", "completed", "failed", "cancelled"):
        status_counts[f"scans_{status}"] = await session.scalar(
            text("SELECT COUNT(*) FROM scans WHERE status = :s"),
            {"s": status},
        )

    return {
        "status": "ok" if db_ok else "degraded",
        "db": "ok" if db_ok else "error",
        "last_scan_at": last_scan,
        **status_counts,    # scans_pending, scans_running, scans_completed,
                            # scans_failed, scans_cancelled
    }
```

**Why explicit per-status counts instead of a dict:** A monitoring
tool or dashboard querying `/healthz` should be able to alert on
`scans_failed` rate or `scans_cancelled` rate without parsing a
nested dict. The 5 fields are a stable interface — adding a
sixth status in 0.3.0 would be a breaking change to the response
shape, which is intentional (it forces a conscious decision to
update monitoring configs).

**Caveat for the per-status implementation:** the `for status in
(...)` loop above executes 5 separate `COUNT(*)` queries. For a
table with many scans this is `O(n)` per query. A single
`GROUP BY status` query is more efficient. The spec keeps the
loop form for clarity; the implementation may switch to
`GROUP BY` if profiling shows it matters. The response shape
does not change either way.

The health endpoint is unauthenticated in both modes. It
deliberately exposes no information that is not already
discoverable by listing the API routes; it is intended for Docker
healthcheck and external monitoring.

## 13. Migration plan

  `init_db`. Existing 0.1.x databases upgrade in place.

- `test_security_headers.py` — covers the CSP and other headers

### 14.2 Integration tests

- `test_scan_cancel.py` — start a long-running scan, call
  `POST /api/scans/{scan_id}/cancel`, verify transition to
  `cancelled` within 2s. Also verify idempotency: a second
  call on the now-`cancelled` scan returns 200 with
  `"idempotent": true` in the body, not 5xx.
- `test_scan_cancel_already_completed.py` — let a scan run
  to natural completion (status `completed`), then call
  `POST /api/scans/{scan_id}/cancel`. Assert:
  - HTTP status is 409 Conflict (NOT 200, NOT 5xx)
  - Response body has `error` key containing the substring
    `"terminal state 'completed'"`
  - Response body includes the scan's original `started_at`
    and `completed_at` timestamps so the operator can see
    *when* the scan finished (this is important UX — a bare
    "conflict" with no timestamps leaves the operator
    confused about why their cancel is being rejected)
  - The scan's status is still `completed` in the DB
    (cancel of terminal state MUST NOT change status)
  - Repeat the same test for `failed` status (use a
    synthetic `failed` scan via the fixture, no need to
    actually fail one)
- `test_scan_start.py` — call `POST /api/scans/{scan_id}/start`
  on a `pending` scan; verify it transitions to `running`.
  Also verify idempotency: a second call on a `running`
  scan returns 200 with `"idempotent": true`.
- `test_scan_start_terminal_state.py` — call
  `POST /api/scans/{scan_id}/start` on a scan that is in
  `completed` state. Assert:
  - HTTP status is 409 Conflict
  - Response body has `error` key containing
    `"terminal state 'completed'"`
  - Response body directs to `POST /api/scans` for creating
    a new scan
  - Repeat for `failed` and `cancelled` source states
- `test_init_lan_warning.py` — run `init` with `--bind 0.0.0.0`,
  verify interactive prompt behaviour, verify security.log entry

### 14.2.1 Test fixtures — `cancelled` must be represented

`tests/conftest.py` currently has no scan fixtures. Add a
`sample_scans` fixture (or equivalent) that creates a scan for
each of the 5 valid statuses: `pending`, `running`, `completed`,

- The `/healthz` response shape test (§9) exercises the

- The `/api/scans` list view test exercises the `cancelled`

- The `audit_log` consumer impact test for `scan.cancel` (§7.2
  action enum) has a real `target_id` to reference
- The frontend type-union exhaustiveness check
  (`ScanStatus = ... | "cancelled"`) compiles against real data

### 14.4 Security review checklist

Before tagging 0.2.0, **all** of the following must be true and
ticked. Each item is a test that must pass; none are "we'll
check at code review time":

- [ ] **Fail-closed at startup is exercised by a test.** A
      dedicated test (`test_server_fail_closed.py`) configures
      `bind: 0.0.0.0` with no `auth.api_key_hash` in config, no
      `REDVEIL_UI_API_KEY` env var, and no `~/.redveil-ui/.api_key`
      file. The test calls the server-startup function and
      asserts that the call **raises `AuthConfigError`** (or
      equivalent — a new exception class defined in
      `redveil_ui/api/middleware.py` for this purpose) — not a
      warning, not a `print` followed by normal startup, but a
      hard exit. The test also asserts that **no listening
      socket has been opened** (verify via
      `socket.SO_REUSEADDR` check or a port-binding probe).
      Conversely, a sibling test confirms that with
      `bind: 0.0.0.0` AND an API key in any of the three storage
      locations, startup succeeds. This pair of tests is the
      explicit guarantee that the fail-closed behaviour is
      real, not aspirational.

      The `AuthConfigError` exception's message is asserted
      verbatim, with a single configurable substring for the
      runtime bind address. The exact format is:

      ```
      Refusing to start: bind={bind} requires authentication.

      redveil-ui will not bind to a non-loopback address without
      an API key. To fix this, do one of:

        1. Set REDVEIL_UI_API_KEY environment variable, OR
        2. Run 'redveil-ui init' to generate a key (existing
           config is preserved), OR
        3. Set 'auth.api_key_hash' in ~/.redveil-ui/config.yaml
           (sha256 hex digest of the raw key).

      For more information, see the LAN deployment section in
      the README.
      ```

      The test asserts:
      - Exception class is `AuthConfigError` (not a generic
        `RuntimeError` or `ValueError`)
      - Message starts with `"Refusing to start: bind={bind}"`
      - Message contains the substring `"requires authentication"`
      - Message contains `"REDVEIL_UI_API_KEY"` and `"redveil-ui init"`
        and `"auth.api_key_hash"` (all three remediation paths
        are surfaced)
      - Message contains `"LAN deployment section"` so the
        user is pointed to documentation
      - Process exit code is non-zero (1, via `SystemExit(1)`)
        when the fail-closed path is hit from CLI entry point,
        not just from the import-level call

      The error message text is also asserted by a separate
      "snapshot test" (`test_auth_error_message.py`) that
      compares the message against a committed golden string
      in `tests/fixtures/auth_error_message.txt`. This catches
      accidental edits to the message that would degrade UX
      (e.g. dropping a remediation step, dropping the docs
      pointer) before they ship.
- [ ] All new endpoints have explicit auth requirements in
      OpenAPI schema
- [ ] No API key or session cookie is logged in any code path
      (grep test: scan all log statements for `%s` / `{}`
      formatters near `api_key` / `cookie` / `session` / `auth`
      identifiers)
- [ ] CSP and other security headers verified against the
      built frontend (Playwright assertion on a real response)
- [ ] Rate limiter cannot be bypassed by `X-Forwarded-For` from
      untrusted sources (test: send request with
      `X-Forwarded-For: 1.2.3.4` from a non-trusted source IP,
      assert the rate limit applies to the actual source IP,
      not the spoofed one)
- [ ] Cookie expiry is enforced server-side, not just by the
      browser (test: forge a cookie with `issued_at` 25h in the
      past, assert 401)
- [ ] `redveil-ui rotate-key` invalidates all existing sessions
      (test: login, get cookie, rotate key, attempt request
      with old cookie, assert 401)
- [ ] All 11.1.1 consumer sites have been updated. A grep
      audit test asserts that no `switch` / `case` / ternary
      over `scans.status` references the old value set
      `{pending, running, completed, failed}` without also
      handling `cancelled`.

## 16. Open questions and future work

### 16.1 Open for 0.2.0 (to resolve during implementation)

- **Cookie `Domain` attribute.** By default, no `Domain`
  attribute is set, which scopes the cookie to the exact host
  the operator types. If the operator accesses via both
  `192.168.1.50:8000` and `redveil.lan:8000`, two separate
  cookies are stored. This may be surprising. Decision: do
  not set `Domain` by default; document.
- **Library orchestrator cancel signal.** §5 / §11.1.1 row B10
  depend on the redveil library exposing a cancel-by-scan-id
  signal. If that signal does not exist in the library at the
  time 0.2.0 work begins, the prereq PR to the library must
  land first. Decision: confirm library status before starting
  §5.
